    Target:

        Give the harness home its own volume mount, separate from the project
        source mount, so a container can have either one without the other.

    Result:

        Work in progress ...

# -----------------------------------------------------
# What was wrong.
#[root@lithosia-dsh-pod]

    DSH_HOME was set to /Zarquan/lithosia-quadra/dsh, a path *inside* the
    source mount. The state was therefore reachable only as a subdirectory of
    the project source, a container had to mount the whole source tree to get
    its own configuration, and the source mount had to be read-write for the
    harness to persist anything. One mount was doing two jobs, and the harness
    home could not be used by a container that did not want this project's
    source.

    DSH_HOME now names the harness home at a fixed container path, /opt/dsh,
    with its own --volume. The host state stays where it was, at
    ${LITHOSIA_CODE}/dsh (gitignored), so nothing had to be moved and no
    existing profile or session was touched.

# -----------------------------------------------------
# The two mounts.
#[root@lithosia-dsh-pod]

        LITHOSIA_CODE   the project source, /Zarquan/lithosia-quadra
        DSH_HOME        the harness home, /opt/dsh, from ${LITHOSIA_CODE}/dsh

    Three launch variants, all documented in README.md:

        both            source and harness home, for an agent that edits this
                        project
        source only     to read or edit with no harness
        harness only    the harness home alone, for agents working on other
                        mounted projects

    The last one is the point of the change: the harness no longer needs this
    project's source in order to run.

    The two that matter:

        The inode check proves both paths are one host directory, so the state
        is not a copy and nothing was migrated.

        The session log mtime matching the current time, and the log growing,
        proves the harness is writing into the mounted home. That is the
        property the whole arrangement depends on.

    The check that fails, and why it is not a fault:

        touch /opt/dsh/.sandbox-probe
        touch: cannot touch '/opt/dsh/.sandbox-probe': Permission denied

    That is the DSH file sandbox, not the mount. Under the `workspace-write`
    policy the writable roots are the session workspace (/Calycopis here) plus
    /tmp and the per-user temporary directory, and nothing else:

        writableRoots(policy) = [ policy.workspaceRoot, "/tmp", tmpdir() ]

        @deepseek-ai/dsh-sandbox, lib/index.js

    So an agent whose workspace is a project cannot write DSH_HOME however it is
    mounted, and a denial there says nothing about the volume. The harness
    itself is not confined this way, which is why it can persist sessions while
    the agent's own shell cannot write the same directory. Do not widen the
    workspace to include DSH_HOME to make such a test pass; if a direct write is
    ever needed, use the bash tool's sandbox_permissions escalation and let the
    user approve that one command.

    Still to check, on the host:

        harness only variant    the DSH_HOME mount with no LITHOSIA_CODE mount.
                                The mechanism is proven, the reduced variant is
                                not.
        source only variant     the LITHOSIA_CODE mount with no DSH_HOME.
        a fresh home            init-dsh.sh against an empty DSH_HOME, which is
                                what a new user does first.

    Do not test any of these by launching containers from inside the DSH
    container. Doing that through the mounted Podman socket destabilised the
    session container twice on 2026-10-09 and it needed restarting both times.
# -----------------------------------------------------
# Caveats worth knowing.
#[root@lithosia-dsh-pod]

    a. The pnpm workspace state file under profiles/web/node_modules records
       the absolute profile path. init-dsh.sh rewrites it; if a plugin install
       misbehaves after the move, run /usr/local/bin/init-dsh.sh again.

    b. Historical manifests under dsh/backups/ name the old path. They are
       records, not configuration.

    c. One harness home, one running harness. Two containers sharing a home
       will corrupt session state; the separate mount makes per-agent homes
       easy (dsh-<name>).

    d. /opt/dsh currently holds an empty pnpm/store directory in the image.
       The mount shadows it, which is harmless.
